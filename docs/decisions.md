# AI provider integration checklist
1. Check official OpenAI Decisions API docs for endpoint, model availability, supported question schemas, response fields, and current pricing.
2. Map `predicate`, `choice`, `score` to normalized result `{criterion_id, status, value, confidence?, evidence_message_ids?}`. Evidence may require a separate extraction step; never pretend Decisions returned citations it did not.
3. Store raw provider response only if privacy policy permits; otherwise store minimal normalized output and diagnostic metadata.
4. Version provider adapter, prompt templates, rubric, model, and scoring mapping.
5. Provider uncertainty is **not** the business score; mapping must be configured in rubric.
6. Responses API for structured extraction and summaries only when needed; batch or cache long-session summaries.
7. Implement retries for transient errors, backoff with jitter, circuit breaker, timeouts, rate limits, and spending gates.

# Prompt improvement, stage 3: the whole improved prompt, and keeping it as a version (console v0.61.0, decided 2026-11-16)
The first real run showed what was missing: the suggestions said what to change per criterion but the person had no prompt to take. The same call now also writes the **whole improved prompt**, and the console can keep it as a version.
- **Same call, more output:** the schema gets a required `new_prompt` (the improved prompt, ready to use). The rules (version `responses-suggestion-v2`) say: apply the suggested changes keeping the structure, language and tone; invent no fact about the business (prices, policies, names, links, hours): write `[PREENCHER: what is missing]`; only the prompt itself, no comments; masked data stays masked. An answer without a usable `new_prompt` (empty, or longer than `MAX_NEW_PROMPT_CHARS`) is an unusable answer: an error type, charged when the provider answered, no result stored. The worker never cuts the text: a prompt that is cut is not a prompt.
- **The cost grows with the prompt, and the gates say so:** the room for the output is `criteria x 450 + 400 + 1.5 x the prompt's tokens` (a prompt may grow by up to half), at most 16,000 tokens (`sci_core.suggestion.max_output_tokens`). The console estimates with the same numbers (generated into its catalog) and the worker's pre-flight uses the same function on the text that will really be sent, so a ceiling that covers the estimate passes the gate. At the dearest rates the whole improved prompt adds about US$ 0.008 (500-token prompt), US$ 0.03 (2,000) and US$ 0.075 (the 20,000-character limit) with `gpt-4o`; a long prompt with many criteria can pass the worker's ceiling (US$ 0.10) and is then refused with the numbers.
- **Result screen:** the improved prompt comes first, whole and read-only, with **Copiar** (the clipboard first; when the sandboxed frame refuses it, the text is selected and copied; when nothing works the person is told to use Ctrl+C), the count of pieces `[PREENCHER: …]` left to fill in, and the reminder that masked data comes back masked. The panel scrolls into view when it opens (it opens below the list). A result made before this version has no `new_prompt`: the screen says so and offers nothing to keep.
- **Keeping it as a version (ADMIN, like the result):** `promptImprovement.saveNewVersion` takes the request and a name. The text is read from the STORED result, never from the caller, so only what the AI wrote for that request can be kept. The name defaults to the original prompt's (when it was kept): an existing name gets the next version (the same text already kept is not stored again and the person is told), a new name is a new prompt, version 1. It reuses the rule of the request: a kept prompt is found by name, any editor may open it (audited). A new prompt longer than 20,000 characters (the limit of a kept prompt) is refused with the instruction to copy and adjust it. The audit trail gets the request, the prompt, the version, the hash and whether a version was created, never the text.
- **Also in this version (v0.60.1):** `gpt-4o-mini` is marked validated in the catalog (it ran for real as the writer of the evidence, the general evaluation and the suggestions). The mark is one flag for every use of a model: its first use as the model of an ANALYSIS through the Responses provider is still untested.
- **Not done, on purpose:** a diff between the old and the new prompt; sending the new prompt straight back to a new request; deleting a kept prompt; filling the `[PREENCHER]` pieces on the page.

# Prompt improvement, stage 2 (executor): the suggestions are written by the on-demand worker (console v0.60.0, decided 2026-11-16)
The requests recorded since v0.59.0 now get their suggestions. The on-demand worker (`sci-<env>-executor`, polled every 10 minutes) takes a REQUESTED row of `prompt_improvement_requests` and makes ONE call to the Responses API; the console opens the result.
- **The numbers are frozen in the request:** the console stores the aggregate (`aggregate`, a JSON column added at the end of the table) the person saw and approved the cost on, and every later row of the request carries it. The worker sends exactly that, so what was approved is what is sent and the page's numbers cannot differ from the AI's (the alternative, recomputing them in Python, would have duplicated the preview's SQL in two languages). A request without it (made by v0.59.0) is refused with "faça o pedido de novo".
- **The same gates as an execution, applied again by the worker (the table is data, not authority):** AI_ENABLED, the key, the month's budget (the shared `ensure_within_monthly_budget`), a model of the closed catalog and of the Responses API only, a ceiling inside the worker's (US$ 0.10), the requester still an active ADMIN, a workspace in `executor_tenants`, and the worst case of the call sized on the text that will really be sent (rules + the prompt as masked + the aggregate in; the full output cap out; the dearest rates) not above the ceiling the person approved. The console estimates with the SAME constants (generated from `sci_core.suggestion` into the console's catalog), so a ceiling that covers the estimate passes the gate.
- **The call:** fixed rules first (the prompt is untrusted data between markers and never obeyed; the numbers are final facts; correlation, not proof; no conversation text exists, so none may be invented; write in Brazilian Portuguese), then the prompt (CPF, CNPJ, e-mail and phone masked, its delimiters neutralised), then the numbers. Strict Structured Outputs; criterion ids are restricted to the ones in the numbers (and dropped again when parsed); lists and texts are cut to their limits instead of failing an answer that was paid for. `store: false`. A refusal, an incomplete or unusable answer is an error TYPE (never text) and is charged when the provider answered; a call that got no answer costs nothing. There is no automatic retry: the person asks again.
- **The spend** is a line of its own in the ledger, `kind = SUGGESTION` (`subject_id` = the request, no session), recorded the moment the provider answers and before anything is stored, so the Painel's "Custo por etapa" shows it like any other step. The request keeps what it cost (`actual_cost_usd`), even when something after the call fails.
- **Order and states:** claim (REQUESTED -> RUNNING, guarded inside the statement, the loser skips) -> gates -> call -> spend -> the result row -> COMPLETED. The result is stored before the request says COMPLETED. A failure is FAILED with a reason that never carries text (the error type only).
- **The text of a prompt that was not kept** is deleted when the request ends, however it ends (COMPLETED, FAILED, refused), and when it is cancelled. A worker that dies mid-call leaves the request RUNNING and the text behind; the workspace cleaner removes it.
- **IAM, narrow and honest:** the worker may append to `prompt_improvement_requests` and `prompt_improvement_results` and delete in `agent_prompts`. BigQuery cannot limit a table permission to some rows, so that it deletes only `NOT retained` rows is the statement's guard (tested), not something IAM enforces. It still cannot touch rubrics, policies, users or the audit trail.
- **Reading the result** (ADMIN, like the list) is audited (`promptImprovement.openResult`: the request and the number of criteria, never the text) and fails closed. The page says the suggestions are hypotheses, written by an AI, to be revised before use.
- **Expected cost:** US$ 0.004 to 0.05 per request at the catalog's highest prices (for 9 criteria: US$ 0.0043 to 0.0488 with `gpt-4o`); no new recurring resource (the same job and the same scheduler).
- **Not done, on purpose:** automatic retry; a rewritten prompt ready to paste; sending conversation excerpts; deleting a kept prompt.

# Prompt improvement, stage 2 (base): the prompt, the estimate and the request, with the AI fed numbers only (console v0.59.0, decided 2026-11-16)
The page now takes the prompt of an agent and records a request for suggestions. **Nothing in this version calls the AI**: the executor that writes the suggestions comes next, and until then a request stays waiting (REQUESTED) and can be cancelled.
- **What the AI will receive: the prompt and numbers, never conversation text** (the user chose this for the first version; excerpts may come later as an option). The aggregate is the stage 1 preview without its examples: per criterion the weight, required/minimum, applicable evaluations, mean score, % weak, % without evidence, % not applicable, % below minimum, points lost and the distribution of ANSWERS (the rubric's own option labels), plus the sample counts. The seller is sent only as "a filter was applied", not by id. `aggregateOf` in `promptImprovement.ts` is that contract; the cost estimate is sized on it.
- **One call, the Responses API** (the API that writes free text, as the general evaluation does), a model of the closed catalog (`gpt-4o` and `gpt-4o-mini`, both validated: `gpt-4o-mini` ran for real on 2026-11-16 as the writer of the evidence, the general evaluation and the suggestions). Estimate = fixed rules (900 tokens) + the prompt + the aggregate in; out, the worst case of 450 tokens per criterion + 400. At the catalog's highest prices that is about US$ 0.004 to 0.03 per request for a rubric of 4-8 criteria and a prompt of a few paragraphs. The request's ceiling must cover the worst case (like an execution) and cannot pass the console's ceiling (`exec.maxCostUsd`).
- **Who may do what:** an EDITOR may paste a prompt, read the models, see the estimate, keep prompts and open them; only an ADMIN may authorise the spend (request, cancel, list the requests), as with an execution: the ceiling and who approved it are administrative data. This is narrower than "EDITOR or ADMIN" in stage 1 and can be widened.
- **The prompt text is sensitive:** it is stored only in `agent_prompts` (by parameter; BigQuery's own job history still holds the statement), never in a log, never in the audit trail (the audit carries ids, the version, the SHA-256 and the size), and never in the request row (which carries only the hash). A test fails if the text reaches any statement but the one that stores it.
- **Keep or not:** the person chooses (and names it) when pasting. A kept prompt is found by its NAME: the same text reuses it, a changed text is its next version; any editor of the workspace may open it, which is audited (`promptImprovement.openPrompt`, fails closed). A prompt that is not kept lives for its request only: it is deleted when the request is cancelled (and, in the next version, when the executor ends it); if a cancel cannot delete it the request is cancelled anyway and the workspace cleaner removes it.
- **Guards:** at least 30 analyses in the sample (the stage 1 minimum, now enforced: below it a request is refused), a prompt of 20 to 20,000 characters, at most 3 waiting requests per workspace, an identical request (same sample, prompt hash and model) refused, an explicit confirmation. The prompt being written survives a new search of the preview.
- **The cleaner:** `clean_workspace.py` deletes the suggestions' results (they come from the analyses), keeps the requests (a history, like `run_requests`) and the kept prompts, and deletes only the text of prompts that were not kept (a leftover of a failure).
- **Also in this version (v0.58.1):** number fields keep what is typed (`0,08` can be typed); needed for the ceiling.
- **Not done, on purpose:** the executor and the AI call; the screen of suggestions; deleting a kept prompt; sending excerpts of conversations.

# Cost by step: every paid call is a line, in every screen (console v0.57.0, decided 2026-11-16)
The cost of an analysis (`session_analyses.estimated_cost_usd`) was one number: the analysis, the evidence call and the general evaluation added together and all shown under the analysis model (`gpt-6-luna`), even though the other two are paid to `gpt-4o-mini`. The console did not read the spend ledger (`ai_spend`) at all. Nothing was missing from the totals; what was missing was transparency.
- **Ledger lines per step:** `ANALYSIS` (the analysis call), `EVIDENCE` (new: the call that cites the messages, with its own model; it used to be inside `ANALYSIS`), `SUMMARY` (the general evaluation) and `ROUTING`. The provider reports the evidence part of its response (`evidence_usage`, `evidence_model`) and the engine records the analysis line as the response minus that part, so the lines add up to exactly what the response cost: totals, ceilings and the monthly budget do not move. Before 2026-11-16 the evidence call is inside the `ANALYSIS` line of the old rows; the screens say so.

- **Read-only, no schema change:** the console reads the ledger it already had permission on (tenant filter on every statement, the session and run reads bounded by time and by the analyses involved); an environment without the ledger shows no lines instead of an error.
- **Tests:** the ledger lines add up to the analysis total (with and without evidence and general evaluation); the provider reports the evidence part separately; every new read is tenant-scoped; the estimate by step adds up to the estimate.

AGENTS.md asks that historical and live produce equivalent results for the same session and rubric. A check on `org-test` found a gap: all 122 on-demand analyses had **no evidence** (the messages cited for each answer) and the executor was **not** writing the general evaluation, while the live service did both (`live_evidence_model` and `live_summary_model` were `gpt-4o-mini`, the executor had neither).

The historical command line got the same `--evidence-model`. - **Known follow-up:** the console decides "já feitas" by model only, so after turning evidence on a window already analysed would show nothing to process. Re-analysing the existing analyses with the new identity needs a console option (or a one-off command); until then new windows (not yet analysed) get the full recipe.

# Prompt improvement, stage 1: the free preview (console v0.55.0, decided 2026-11-14)
A page, **Melhorar prompt** (EDITOR or ADMIN, group Análise), shows where the agent loses points in the criteria of a published rubric version, from the analyses that already exist. Stage 1 only reads; it calls no AI and spends nothing. The next stages turn the numbers into suggested changes to a prompt the person gives.
- **Scope of a question:** a published rubric version + a period of analyses (at most 366 days, by the day the analysis started, like `sql/analysis`) + an optional seller (the seller on the latest row of each session; sessions are read up to 365 days before the period, because a historical run analyses old sessions). Only COMPLETED analyses, the latest of each session.
- **Every number is counted in BigQuery and computed in the server, never by an AI:** analyses, sessions, mean score, approval; per criterion the applicable evaluations, mean score, % weak (below 60, the limit of `sql/analysis/02`), % without sufficient evidence, % not applicable, % below the criterion's own minimum, the distribution of answers and **points lost**.
- **Points lost** = how many points of the overall score (0-100) the criterion cost on average: for each analysis, weight x (100 - score) divided by the weight of everything that applied in that analysis, averaged over all analyses of the sample (an analysis where the criterion did not apply counts as 0). The criteria's points lost add up to what the sample lost of the overall score, so they rank where a prompt change would pay most. Gates (weight 0) measure no quality and are listed last.
- **Thin samples are said, not hidden:** below 30 analyses in the sample, or 30 applicable evaluations of a criterion, the page warns / marks the criterion "amostra pequena". Correlation, not proof of cause: the page states it is a preview and not a verdict.
- **Examples** (3 worst or best cases of a criterion, with the messages cited as evidence): masked (CPF, CNPJ, e-mail, phone) and cut to 280 characters; reading them is **audited** like opening a session (ids and counts only, never text) and **fails closed** (no audit, no text).
- **Contract fixed now:** three tables, created empty (cost nothing): `agent_prompts` (versions of the prompts people give; `retained` = kept by choice, otherwise deleted when its request ends), `prompt_improvement_requests` (append-only status history per request, like `run_requests`) and `prompt_improvement_results` (the aggregate sent, the validated suggestions, model and tokens). DDL in `sql/08_prompt_improvement.sql`; Terraform schemas are derived from it and a test fails on drift.
- **Open for stage 2 (not decided, nothing implemented):** whether masked conversation excerpts may be sent to the AI (the route the evaluations already use) or only numbers and answers; the sample minimum is 30 as proposed; the result is in Portuguese; the prompt text of a request that is not kept is deleted when the request ends.

# The sign-in screens (console v0.58.0, decided 2026-11-16)
The console is an Apps Script web app that **executes as its deployer** and is limited to the Workspace domain (`executeAs: USER_DEPLOYING`, `access: DOMAIN`). So **Google authenticates, before any code of ours runs**, and a screen of ours cannot replace Google's sign-in page nor sit in front of it; the table `app_users` authorises, on the server, on every call. What can be ours, and is now elegant and on-brand, are the screens after Google lets the person in:
- **Entrando…** while the console asks who the person is and what they may open (an announced status, instead of a blank page).
- **Conta não reconhecida:** Google gave an account the console cannot use (none, or outside the company domain: the usual cause is a browser with several Google accounts). Button **Escolher outra conta** opens Google's account chooser and comes back to the console (the other accounts stay signed in). The server draws the same page itself (`gatePage.ts`: plain HTML and its own stylesheet, no script, no font, no image, only that one address) because no script of the console exists yet at that point.
- **Você ainda não tem acesso:** the account is Google's and recognised but no row of `app_users` gives it a workspace. Shows whose account it is (name and e-mail), says access is granted by an administrator and offers **Solicitar acesso** (a mail to `ACCESS_CONTACT_EMAIL`, optional script property, validated; the account is in the message) and **Usar outra conta**. Without the property the screen says to ask an administrator to add the e-mail in Usuários e acesso.
- **Não foi possível entrar:** any other failure (BigQuery down, configuration) is not blamed on the account: **Tentar de novo**, with the request code.
- **Nothing here decides access:** a person who reaches the console still needs an active row of `app_users`, checked by the server on every call; a revoked one is refused within 30 seconds as before. The web app's own address comes from Apps Script (`ScriptApp.getService().getUrl()`), checked against the shape of an Apps Script address before it is put in a link, and is handed to the page in the template, never read from a request.
- **Security contract, extended narrowly:** the test that lets only the account menu open another window now also lets the sign-in screens, with exactly one call (`window.open(accountChooserUrl(back), "_top")`). The bundle budget went from 280 KB to 300 KB (it was at 280 KB with the date picker, skeletons and cost by step).
- **Not done, on purpose:** an "always show a welcome with Continuar como…" screen before the console (an extra click for everyone every session); a custom OAuth login (it would mean giving up `DOMAIN` access and writing our own session handling, a larger risk than the benefit).

# The audit trail is cleared by its own process (decided 2026-11-14)
`scripts/clean_workspace.py` keeps deleting only data (conversations and results) and never the audit trail. Clearing the trail of a test workspace is `scripts/clean_audit.py`, separate on purpose: cleaning data must not erase the evidence by accident, and clearing the evidence is a decision of its own.
- Dry run by default; `--apply` deletes that workspace's `audit_log` rows (`--before YYYY-MM-DD` limits it to older events); organization and workspace are bound parameters.
- It leaves **one** event, `audit.clean` (actor `script:clean_audit`, with the rows removed and the cut-off), written after the check that nothing else stayed, so the trail always says it was cleared and when. Nothing is written if rows stayed.
- Only test organizations (`synthetic-*`, `org-test`); there is no flag to clear the trail of any other organization, unlike `clean_workspace.py --allow-any-tenant`: the evidence of a real tenant is not erased by a script. `clean_synthetic.py` also still protects `audit_log`.
- Not run: the scripts only exist; applying them needs an explicit go-ahead.

# Faster pages: concurrent blocks and a short read cache (console v0.51.2, decided 2026-11-14)
Measured in BigQuery job history (3 days): each console query takes 170–420 ms and reads kilobytes, mostly from the query cache. The wait of a page is the **number of queries run one after the other** inside one Apps Script call (Painel: 5; Como funciona: 14, about 4–6 s).
- **Concurrent blocks:** `dashboard.summary` and `pipeline.overview` accept `parts` (the blocks wanted; none = all, as before; an unknown block is refused). The pages ask for their blocks in 3–4 calls at once and merge the answers, so the wait is the slowest call. A failed call fails the page.
- **Short cache, in the server:** `CacheService` (script cache) keeps a successful answer of `dashboard.summary`/`dashboard.score` for **120 s** and of `pipeline.overview` for **60 s**. The key is the workspace + whether the caller is ADMIN + the whole question (stable order); it is read only **after** the caller was authorised for that workspace. The executor queue and the schedules blocks are live figures and are never cached; writes, errors and values over 80 KB are never cached. `fresh: true` skips it. Trade-off: those numbers can be up to 2 minutes old.
- No new resource, no extra BigQuery cost (fewer queries, not more); the number of calls per page grows (3–4), within the read limit (240/min).

# The weights of a rubric add up to 100 (editor rule, decided 2026-11-14)
The weights of the **enabled** criteria of a rubric must add up to exactly 100, neither under nor over (a tolerance of 0.000001 absorbs decimals such as 33.3 + 33.3 + 33.4). It is a rule of the console editor, not of the Python engine: the engine still reads any rubric already published, and the shared conformance cases with the console do not include it.
- A draft may be saved with the total pending (it is work in progress) and the editor says how far it is ("faltam 40" / "passam 20"); **publishing is refused** while the total is not 100 (`rubrics.publish` fails on any pending issue), and a rubric cannot be created valid without reaching 100.
- Disabled criteria do not count; zero-weight gate criteria (`is_sales`, `has_objection`) do not move the total.
- No published rubric breaks: all 19 versions in dev already add up to 100. A new revision copied from a version that did not would show the pending total until it is adjusted.
- Unchanged: at scoring time the weights of the criteria that do not apply (or lack evidence) leave the calculation and the remaining ones are normalized, so the 100 is the rubric's budget, not the denominator of every analysis.

# A required criterion is judged by its own minimum (decided 2026-11-14; replaces the rule below)
Until then a **required** criterion was compared with the rubric's `minimum_approval_score`, the minimum of the whole analysis, although nobody had defined a minimum for the criterion. A middle level (50) on a required criterion rejected an analysis whose weighted average passed.
- `evaluation_criteria.minimum_score` (FLOAT64, nullable, 0..100) is the criterion's own floor, set in the rubric and part of the immutable version. Only a **required** criterion may have one, and it must be reachable (not above the best answer).
- A required criterion **with** a minimum rejects the analysis when its score is below it. **Without** one it only has to be evaluated: missing evidence still goes to review (never zero), and a low score does not reject by itself. The overall minimum still decides on its own.
- `REQUIRED_CRITERION_BELOW_MINIMUM` now carries `minimum` (the criterion's own). Analyses stored before have no `minimum` in the reason, and the console words them as the rule of that time (`scripts/backfill_approval_reason.py` rebuilds old reasons that way).
- Nothing already stored is rewritten. Published rubrics are immutable, so their required criteria have no minimum: from the deploy of the new engine on, a new analysis under them is no longer rejected by a low score on a required criterion. To keep the old strictness a rubric needs a new revision with a minimum on that criterion. The snapshot hash of a rubric whose criteria have no minimum is unchanged.
- Schema: one nullable column appended to `evaluation_criteria` (`terraform plan`: 0 add, 1 change, 0 destroy), applied before the engine and the console that read it. Plan, cost and order: `docs/deployment-plan.md`.

# Approval reason is persisted (session_analyses.approval_reason, JSON)
A 87.5 analysis can be REJECTED: a **required** criterion below `minimum_approval_score` rejects regardless of the weighted average (the rule until 2026-11-14, see the decision above). The status alone hid why,
so `calculate_score` now returns `approval_reason = {minimum, overall, reasons[]}` and the engine stores it next to the status.
- Reason codes are fixed (`REQUIRED_CRITERION_BELOW_MINIMUM`, `OVERALL_BELOW_MINIMUM`, `MEETS_MINIMUM`, `INSUFFICIENT_EVIDENCE`, `NO_APPLICABLE_CRITERIA`) and carry criterion ids and
  scores only: no conversation text, so no PII. The decision itself is unchanged (a test pins it).
- The column is the last one in the table (BigQuery only appends columns), nullable, so analyses written before it existed have NULL and the console shows no reason for them.
- The console re-parses and rebuilds the JSON from known fields before showing it (it never renders stored text as-is) and explains the reason in Portuguese on the session and review screens.
- Expected cost: none (a few bytes per analysis). Infra: one in-place schema change (`terraform plan`: 0 add, 1 change, 0 destroy), applied per environment only with approval.
